Browser Isolation

Self-hosted remote browser isolation (RBI). Users sign in to a portal, launch an isolated browser in a container (Podman or Docker), and interact with it through a custom WebRTC viewer in their own browser. Malicious pages stay inside the container; the user’s machine only sees a stream.

This repo is an npm workspaces monorepo:

PackagePathRole
orchestratororchestrator/Fastify API, auth, SQLite, Docker lifecycle, session proxy, optional worker agent
webweb/React SPA (dashboard, viewer, admin)

Isolated browsers are Neko containers (ghcr.io/m1k1o/neko/*).

What you get

  • Local username/password auth (SQLite), with optional SAML 2.0 SSO
  • One isolated browser session per user (Chrome, Firefox, Brave, and the rest of the Neko catalog)
  • Custom WebRTC viewer (signaling proxied through the portal; media to the host mux ports)
  • Admin: join/terminate sessions, users, browsers, settings, profile volumes, workers, audit log
  • Idle reaper + max session lifetime; restart reconciliation of Docker vs SQLite
  • Optional multi-host workers so browsers run on edge machines while one portal stays the control plane
  • Optional persistent profiles keyed by stable subjectId (SAML-ready) — see docs/USER_IDENTITY.md

Prerequisites

  • Podman (recommended) with Compose, or Docker + Compose v2
  • Or Node.js 22+ for local development and unit tests
  • Container engine socket access for the orchestrator (Compose mounts the Podman/Docker API socket)

Production remote hosts: publish via GHCR and auto-start with Quadlet — see docs/PODMAN.md.

Sign in → pick a browser → Launch. The orchestrator starts a Neko container on the rbi-browsers network and proxies /session/:id/view/* after an ownership check (admins may open any session).

Disconnect on a session destroys your container. Portal Log out does the same. Admins use Admin to list sessions, Join, or Terminate; those actions are audited.

Architecture

System design and module map

Architecture

Browser Isolation is a control plane (portal + orchestrator) that starts data-plane Neko containers and streams their desktops to users over WebRTC.

┌─────────────┐     HTTPS / WSS      ┌──────────────────┐
│ User browser│─────────────────────▶│  Orchestrator    │
│  (web SPA)  │                      │  + static UI     │
└──────┬──────┘                      │  SQLite, auth    │
       │                             └────────┬─────────┘
       │ WebRTC media                         │ Docker API
       │ (UDP/TCP mux ports)                  │ or worker /v1
       ▼                                      ▼
┌─────────────┐                      ┌──────────────────┐
│ PUBLIC_IP   │◀── ICE candidates ───│ Neko container    │
│ :52000+     │                      │ (Chrome/Firefox…)│
└─────────────┘                      └──────────────────┘

Signaling and the portal stay on the orchestrator. Media goes peer-to-peer (or via TURN) to the host that runs the container.

Packages

Orchestrator (orchestrator/)

Node 22 + Fastify service that:

  • Authenticates users (local bcrypt and optional SAML)
  • Stores portal sessions, browser sessions, settings, workers, audit in SQLite (better-sqlite3)
  • Creates/destroys Neko containers via dockerode (local) or remote worker agents
  • Reverse-proxies /session/:id/view/* (HTTP + WebSocket) to Neko after ACL checks
  • Runs a background reaper and, on boot, reconciles DB rows with labeled containers
  • Optionally runs as a worker agent (worker-main.ts) exposing /v1/*

Entry: src/index.ts (portal) · src/worker-main.ts (agent).

Web (web/)

React 19 + Vite SPA:

  • Login / dashboard / session viewer / admin console
  • Typed API client (api.ts) with CSRF headers
  • Custom Neko WebRTC client under viewer/

In production the orchestrator serves web/dist. In development Vite proxies API and view traffic to :8080.

Neko containers

Official images ghcr.io/m1k1o/neko/<browser>:<tag>. Each session gets:

  • A Docker container on network rbi-browsers (default)
  • One host WebRTC mux port (UDP + TCP) from WEBRTC_PORT_RANGE
  • Injected managed policies from orchestrator/neko-policies/
  • Optional named volume for a persistent browser profile

Request path: login → stream → disconnect

sequenceDiagram
  participant U as User
  participant SPA as web SPA
  participant O as Orchestrator
  participant W as Worker / local Docker
  participant N as Neko

  U->>SPA: Credentials or SSO
  SPA->>O: POST /api/auth/login (or SAML ACS)
  O-->>SPA: Set-Cookie rbi_session

  U->>SPA: Launch browser
  SPA->>O: POST /api/sessions + CSRF
  O->>W: Create container + allocate port
  W->>N: Start Neko
  O-->>SPA: session id

  SPA->>O: POST /api/sessions/:id/access
  O-->>SPA: wsPath, Neko password, ICE servers
  SPA->>O: WSS /session/:id/view/ws
  O->>N: Proxied WebSocket
  Note over SPA,N: WebRTC media to PUBLIC_IP:webrtcPort

  U->>SPA: Disconnect
  SPA->>O: DELETE /api/sessions/mine
  O->>W: Remove container

Mermaid diagram source — render in GitHub/compatible viewers, or follow the ASCII diagrams nearby.

Important invariants:

  1. One browser session per portal user (browser_sessions.owner_username UNIQUE). Launch reconnects if the container is still up.
  2. ACL: owner or admin (access.ts). Proxy uses the portal cookie, not CSRF.
  3. Viewer credentials are Neko admin password + display name rbi, not the portal password.
  4. Logout destroys the user’s browser container.

Workers and placement

  • Default: orchestrator is also worker id local (LOCAL_WORKER_ENABLED=true).
  • Remote agents: Bearer-authenticated /v1/* on WORKER_PORT (default 8090).
  • Scheduler picks the online enabled worker with the lowest activeSessions (sticky id tie-break).
  • Persistent profiles prefer the worker recorded in profile_placements.

Details: WORKERS.md.

Debugging tips

Browser won’t stream

  1. Confirm PUBLIC_IP is reachable from the client on the WebRTC port range (UDP and TCP).
  2. Check orchestrator logs for container create / Neko readiness failures.
  3. In the browser, inspect WebRTC ICE failures (candidates pointing at the wrong IP).

403 csrf_failed

  • Mutating /api/* calls need X-CSRF-Token.
  • Logged out: call GET /api/auth/csrf first.
  • Logged in: use csrfToken from GET /api/me (the SPA does this in api.ts).

Launch returns an error about ports

  • Pool exhausted → widen WEBRTC_PORT_RANGE and publish those ports (Compose worker service publishes 52000-52099 by default).

Admin UI missing a feature that the API has

  • Wire web/src/api.ts + a page under pages/admin/. Admin is role-gated in both SPA and API.

Code style

  • TypeScript throughout; orchestrator compiles with tsc, web with Vite + tsc --noEmit.
  • Prefer small focused modules next to existing patterns.
  • Do not commit .env, data/.sqlite, or node_modules / dist (see .gitignore).
  • Keep PRs scoped; match naming and error codes already used in routes (csrf_failed, not_found, …).

Production build check

Before shipping a change that affects packaging:

npm run build
NODE_ENV=production npm start
# or
docker compose up --build

The Dockerfile multi-stage build runs npm ci, builds both workspaces, prunes dev deps, and defaults CMD to the portal (dist/index.js). Workers override the command to dist/worker-main.js.

  1. Portal (orchestrator) — cookies + CSRF for browsers; used by the SPA

Deployment

TLS, firewall, production ops

Deployment

How to run Browser Isolation in production (or anything beyond a laptop).

Production recommendation: Podman + GHCR image + systemd Quadlet (pull :latest on boot). Beginner walkthrough: PODMAN.md.

Recommended topology

Single host (default)

  • One orchestrator service (LOCAL_WORKER_ENABLED=true)
  • Container engine socket mounted (Podman or Docker); WebRTC ports published on the host (or DNAT)
  • Optional reverse proxy for TLS on 443

Split control / data plane

  • Portal host: orchestrator only (LOCAL_WORKER_ENABLED=false)
  • One or more browser hosts: worker profile / worker Quadlet
  • Clients → portal (HTTPS); clients → each worker PUBLIC_IP for WebRTC
  • Orchestrator → worker agents on a private network

See WORKERS.md.

Podman + GHCR (recommended)

  1. Push to main so Actions publishes ghcr.io/thecookies/browserisolation:latest.
  2. On the host: enable podman.socket, podman login ghcr.io, install units from deploy/podman/.

Full steps (token, Quadlet, extra workers): PODMAN.md.

cp .env.example .env
# Edit: PUBLIC_IP, COOKIE_SECURE, TRUST_PROXY, AUTH_USERS (first boot only), etc.

# Podman (default): API socket at /run/podman/podman.sock

# Docker Engine:
# CONTAINER_SOCKET=/var/run/docker.sock docker compose up -d --build

Clients must reach PUBLIC_IP on the WebRTC ports. TLS on the portal does not encrypt the WebRTC media path by itself; use a private network or TURN as needed.

Reverse proxy with TLS

Terminate TLS in front of the orchestrator. Set:

COOKIE_SECURE=true
TRUST_PROXY=true
PUBLIC_BASE_URL=https://rbi.example.com   # required for SAML
PUBLIC_IP=<client-reachable host IP>

Caddy

rbi.example.com {
  reverse_proxy 127.0.0.1:8080
}

Nginx

WebSocket upgrade is required for /session/*/view/ws:

map $http_upgrade $connection_upgrade {
  default upgrade;
  '' close;
}

server {
  listen 443 ssl http2;
  server_name rbi.example.com;

  ssl_certificate     /etc/ssl/certs/rbi.fullchain.pem;
  ssl_certificate_key /etc/ssl/private/rbi.key;

  location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

Podman + GHCR

Publish image and remote auto-pull

Podman + GitHub Container Registry (GHCR)

Run Browser Isolation with Podman instead of Docker, publish the app image from GitHub Actions to a private GHCR package, and auto-pull :latest on a remote host at boot.

Your private GitHub code repo is not a container registry. Pulls use:

ghcr.io/thecookies/browserisolation:latest

The orchestrator still talks to a Docker-compatible API (dockerode). On Podman that is the rootful podman.socket, mounted into the container as /var/run/docker.sock.

What you will end up with

PieceRole
GitHub Actions workflowBuilds Dockerfile on every push to main and pushes :latest + short SHA tags
GHCR packagePrivate image store for the remote host
Remote host Quadlet unitOn boot: pull :latest, start orchestrator (local worker enabled)
Extra hosts (later)Same image, worker Quadlet only — no orchestrator

Part A — Publish the image to GHCR (first time)

1. Push the workflow

The workflow lives at .github/workflows/publish-image.yml. Merge it to main (or push main if you are already on it).

It uses the built-in GITHUB_TOKEN with packages: write. You do not need to create a secret just to publish from this repo.

2. Watch the Action

  1. Open the repo on GitHub → Actions.
  2. Select Publish image.
  3. Open the latest run and wait until it is green.

If it fails on permissions, check Settings → Actions → General → Workflow permissions and allow read/write for GITHUB_TOKEN (or keep the workflow’s explicit packages: write).

3. Find the package

  1. Open the repo → right sidebar Packages, or your org/user → Packages.
  2. Open browserisolation (name may appear as browserisolation).
  3. Confirm the image URI is ghcr.io/thecookies/browserisolation.
  4. Under package settings, keep visibility Private (default for private repos).

Optional but useful: under package Package settings → Manage Actions access, ensure this repository has a role that can write (the publishing workflow needs that once; pull from a remote uses a PAT — next step).

4. Create a pull token for the remote host

The remote machine is not GitHub Actions, so it needs credentials to pull a private package.

  1. GitHub → profile → Settings → Developer settings → Personal access tokens.
  2. Create a classic token with at least:

- read:packages

  1. Copy the token once. Store it only on the remote host (or a secret manager). Do not commit it.

Fine-grained tokens can work if granted read access to the package (and the repo if your org requires it). Classic read:packages is the simplest first path.

Part B — Remote host (orchestrator + local worker)

Assumes a Linux host with systemd (Fedora, RHEL, Debian/Ubuntu with Podman 4+). Use rootful Podman so published WebRTC ports and nested Neko containers behave predictably.

1. Install Podman and enable the API socket

# Example: Debian/Ubuntu
sudo apt update
sudo apt install -y podman

# Example: Fedora/RHEL
# sudo dnf install -y podman

sudo systemctl enable --now podman.socket
sudo ls -l /run/podman/podman.sock

2. Log in to GHCR

export GHCR_TOKEN='paste-your-read-packages-token-here'
echo "$GHCR_TOKEN" | sudo podman login ghcr.io -u TheCookies --password-stdin
unset GHCR_TOKEN

Use your GitHub username (or a machine user) as -u. The token is the password.

Test:

sudo podman pull ghcr.io/thecookies/browserisolation:latest

3. Create the env file

sudo mkdir -p /etc/browser-isolation
# From a checkout of this repo, or paste .env.example contents:
sudo cp .env.example /etc/browser-isolation/browser-isolation.env
sudo chmod 600 /etc/browser-isolation/browser-isolation.env
sudo nano /etc/browser-isolation/browser-isolation.env

Minimum edits before browsers will work for remote clients:

VariableSet to
PUBLIC_IPThis host’s client-reachable IP
AUTH_USERSChange default passwords (first boot only)
COOKIE_SECURE / TRUST_PROXYtrue behind HTTPS
LOCAL_WORKER_ENABLEDtrue (default)

Keep DOCKER_SOCKET=/var/run/docker.sock — the Quadlet mounts the Podman socket at that path inside the container.

4. Install Quadlet units

From a clone of this repo on the host (or copy the files another way):

sudo mkdir -p /etc/containers/systemd
sudo cp deploy/podman/browser-isolation.container \
        deploy/podman/rbi-browsers.network \
        deploy/podman/rbi-data.volume \
        /etc/containers/systemd/

sudo systemctl enable --now browser-isolation.service

Quadlet generates browser-isolation.service from browser-isolation.container.

Pull=always means every unit start (including reboot) pulls :latest before running.

5. Verify

sudo systemctl status browser-isolation.service
sudo podman ps
curl -sS http://127.0.0.1:8080/api/health

Open http://<PUBLIC_IP>:8080 (or your reverse proxy URL). See DEPLOYMENT.md for TLS and firewall ports (8080 / 443, plus WEBRTC_PORT_RANGE UDP+TCP).

6. After you push a new image

Reboot the host, or:

sudo systemctl restart browser-isolation.service

That pulls a newer :latest and recreates the container. SQLite stays on the rbi-data volume.

Part C — Extra worker hosts (later)

Do not install browser-isolation.container on these machines.

  2. Env file with at least:

Workers

Multi-host browser placement

Multi-host browser workers

The portal (orchestrator) schedules isolated browser containers onto one or more worker hosts so load is not stuck on a single machine.

Roles

RoleRunsNeeds
OrchestratorPortal UI, auth, SQLite, session proxyReachability to each worker agent URL
WorkerPodman/Docker + Neko containers + WebRTC portsClient-reachable PUBLIC_IP and open WEBRTC_PORT_RANGE

Single-node installs keep LOCAL_WORKER_ENABLED=true (default): the orchestrator is also worker local.

Networking model

User browser --HTTPS--> Orchestrator --HTTP/WS--> Worker agent --HTTP/WS--> Neko container
User browser --WebRTC UDP/TCP--> Worker PUBLIC_IP:webrtcPort
  • Signaling and /session/*/view stay on the portal (cookie ACL).
  • Media goes directly to the worker that owns the session.
  • Do not expose the worker agent port to the public internet; restrict it to the orchestrator (or a private management network).

The worker service publishes 52000-52099 UDP+TCP by default. Edit the Compose port mappings if your range differs.

Registering workers on the portal

Bootstrap via env (orchestrator host):

WORKERS=edge1|http://10.0.0.5:8090|10.0.0.5|replace-me-with-a-long-secret
LOCAL_WORKER_ENABLED=false   # optional: control-plane-only portal

Or Admin → Workers → Add worker with the same fields (id, agent URL, public IP, token).

The orchestrator polls GET /v1/status every 15s. Workers with a fresh heartbeat (within ~45s) show as online.

Placement rules

Implemented in workers/scheduler.ts + workers/placement.ts:

  1. Consider enabled workers that are online.
  2. Prefer the worker recorded in profile_placements when the user has a persistent profile for that browser (volumes are local to the host).
  3. Otherwise pick the lowest activeSessions (stable id tie-break).

Persistent profiles stick to the worker that first created the volume. Deleting the volume via Admin → Storage clears that placement.

Clients → portal 443/8080TCP

Public → worker agentDeny

Operational tips

  • Each host needs its own free WebRTC port range large enough for peak concurrent sessions on that host.
  • Image pulls: Admin → Browsers → Pull latest fans out to workers.
  • Host metrics: Admin → Workers → status (GET /api/admin/workers/:id/status).
  • If a worker disappears, existing sessions on it become unreachable until the container host returns; the reaper still applies idle/max-age rules from the portal’s point of view (viewer count drops when the proxy cannot stay up).

Identity

subjectId, profiles, SAML

User identity and persistent browser profiles

This document explains how portal users are identified for data ownership (preferences and Docker profile volumes), and how local auth and SAML share the same storage model. For the full doc set, see README.md.

Concepts

FieldPurposeExample (local)Example (SAML)
usernameDisplay / login label shown in the UIalicealice@example.com
subjectIdStable ownership key for prefs + volumeslocal:alicesaml:urn:oasis:…:alice@example.com
profileStorageKeyPath-safe hash of subjectIda1b2… (32 hex chars)same derivation

Rule: preferences and Docker volumes are keyed by subjectId (via profileStorageKey), never by display username alone.

Local auth (current)

Local accounts live in SQLite (local_users), not permanently in .env.

  1. On first boot with an empty local_users table, AUTH_USERS seeds the database.
  2. After that, manage users in Admin → Users (add / role / reset password / delete).
  3. orchestrator/src/auth/local-provider.ts authenticates against the DB and returns:
{ username, role, subjectId } // subjectId is local:<username>

Helpers live in orchestrator/src/auth/identity.ts. When SAML is added, keep this local store as an optional break-glass admin path or disable it via config.

Persistent profiles

  1. Admin enables the feature with PERSIST_PROFILES_ENABLED=true (default).
  2. Each user may opt in via Dashboard → Persist browser settings (PUT /api/preferences).
  3. Preference is stored in SQLite user_preferences.subject_id.
  4. On launch with persistence on, the orchestrator mounts a Docker named volume:

``text rbi-profile-<profileStorageKey>-<browser> ``

Examples:

- rbi-profile-<hash>-chrome - rbi-profile-<hash>-firefox - rbi-profile-<hash>-brave

  1. Volume target paths inside Neko containers (see Neko browser docs):
BrowserContainer path
chrome/home/neko/.config/google-chrome
brave/home/neko/.config/brave
firefox/home/neko/.mozilla/firefox/profile.default
  1. Persist-mode also uses orchestrator/neko-policies/<browser>/policies.persist.json

so cookies/session data are not wiped on browser exit.

Turning persistence off does not delete volumes (data remains if the user opts back in). Destroying a browser session removes the container only, not the profile volume.

Inspecting volumes

docker volume ls --filter label=rbi.managed=true
docker volume inspect rbi-profile-<key>-chrome

Labels on each volume:

  • rbi.managed=true
  • rbi.subject_key=<profileStorageKey>
  • rbi.browser=<chrome|firefox|brave>

SAML / SSO (implemented)

Configure under Admin → Settings → SSO / SAML (or matching .env keys). Implementation lives in orchestrator/src/auth/saml.ts and auth routes.

Security

Threat model and hardening

Security notes

Browser Isolation is a security product. Treat defaults as intentional and review this page before widening trust boundaries.

Threat model (summary)

In scopeOut of scope (today)
Malicious web content inside the isolated browserFully malicious admin with Docker socket access
Cross-user session access via the portalClient-side malware on the user’s machine
Casual data exfil via clipboard/files when disabledPerfect anonymity / anti-fingerprinting of Neko itself

The user’s endpoint should only receive a media stream and input events, not render untrusted HTML/JS from the target site.

Hardening defaults

ControlDefaultNotes
Clipboard syncOff (ALLOW_CLIPBOARD=false)Admin → Settings → Security
Downloads / file transferOff (ALLOW_DOWNLOADS=false)Same
CSRFOn for mutating /api/*SAML ACS exempt by necessity
Session cookiehttpOnly, SameSite=LaxSet COOKIE_SECURE under HTTPS
Browser ACLOwner or adminEnforced in API and view proxy
Managed policiesInjected at createRemoves SponsorBlock force-install; keeps uBlock
Worker agentBearer tokenMust not be public

Trust boundaries

[ User browser ]  --trusted UI/API-->  [ Orchestrator ]
        |                                     |
        | WebRTC (media)                      | Docker socket / worker Bearer
        v                                     v
[ Worker PUBLIC_IP ]  <----- container ---->  [ Neko / target web ]
  • Anyone who can call the Docker socket or forge WORKER_TOKEN can run arbitrary containers on that host.
  • Admins can join any session (by design); audit those actions.
  • SAML trust depends on IdP certificate configuration and PUBLIC_BASE_URL.

Operational checklist

See the checklist in DEPLOYMENT.md. In short: HTTPS, rotate defaults, lock down agent ports, keep exfil toggles off unless required, back up SQLite deliberately.

Reporting issues

If you find a vulnerability in this project, do not open a public issue with exploit details. Contact the maintainers privately with reproduction steps and impact.

Product plan

This document is the map of what is built, why, and sensible next steps so a new contributor can prioritize work without rediscovering history from git alone.

Provide a self-hosted remote browser isolation portal that is:

  • Safe by default (ACL proxy, optional clipboard/downloads off, managed browser policies)

Design decisions worth remembering

  1. SQLite over Postgres — one-node ops simplicity; workers are remote Docker hosts, not another DB.
  2. One session per user — simplifies ACL and UX; reconnect instead of multi-tab containers.
  3. Proxy signaling, not media — orchestrator stays on the path for auth; media scales with worker NICs.
  4. subjectId ≠ username — storage survives display-name / IdP changes; see USER_IDENTITY.md.
  5. Policies as files — neko-policies/ injected at create time; persist mode uses policies.persist.json.
  6. Admin settings in SQLite — ops can tune without redeploying; a small set of infra keys stay env-only.

Key flows

Launch — routes/sessions.ts → browser-sessions.ts → workers/placement.ts → local docker/container-runtime.ts or remote workers/client.ts.

View — SPA calls POST …/access, then opens WebSocket on /session/:id/view/ws. proxy.ts checks ACL (access.ts), tracks viewers (viewer-tracker.ts), and forwards to Neko (or worker /v1/proxy/…).

Cleanup — lifecycle.ts reaper + destroy paths in browser-sessions.ts; logout also destroys.

Config

Loaded from the repo-root .env (see env-file.ts + config.ts). Admin overrides land in SQLite via settings-store.ts / settings-fields.ts.

Worker-only env: WORKER_ID, WORKER_TOKEN, WORKER_PORT (see ../docs/WORKERS.md).

Policies

neko-policies/<chrome|brave|firefox>/:

  • policies.json — default (ephemeral) sessions
  • policies.persist.json — when the user opted into persistent profiles

Catalog and image names: src/neko-browsers.ts.

Web UI

Frontend and viewer

Web

React SPA for Browser Isolation: login, launch dashboard, WebRTC session viewer, and admin console.

Built with React 19, React Router 7, and Vite 7. In production the orchestrator serves web/dist as static files.

Scripts

ScriptCommandPurpose
Devnpm run dev -w webVite on http://localhost:5173
Buildnpm run build -w webTypecheck + Vite production build
Previewnpm run preview -w webServe the production build locally

Prefer npm run dev from the repo root so the API and UI start together.

Dev proxy

vite.config.ts proxies:

  • /api → http://127.0.0.1:8080
  • /session/:id/view/* (including WebSocket) → API
  • /session/:id (no /view) stays on Vite so the SPA shell loads

Cookies and CSRF work same-origin through the proxy.

Talking to the API

All calls go through api.ts:

  • Reads csrfToken from /api/me (or /api/auth/csrf on login)
  • Sends X-CSRF-Token on mutating methods
  • Uses credentials: "include" for the portal cookie

When you add a backend route, add a typed helper here and call it from the page.

Viewer

viewer/RemoteDesktop.tsx mounts the stream. Under the hood:

  1. Parent page fetches access credentials (POST /api/sessions/:id/access or admin join).
  2. Client opens WebSocket to wsPath (/session/:id/view/ws) with Neko username/password.
  3. WebRTC media uses ICE servers from the access response; candidates advertise the worker PUBLIC_IP.

Keyboard mapping includes Guacamole-derived code under Apache 2.0 (LICENSE-APACHE-2.0, NOTICE).
